# Testing strategy for the embedded FTP server

The embedded server needs both unit coverage of the upload-bridging logic (extension filtering, buffer-then-POST-on-`Close`, abort handling, the `MemMapFs` fallback for `RETR`/resume/`DELE` from ADR-0001) and an integration test proving the whole stack — a real `STOR` over a real PASV data connection — reaches a mocked paperless-ngx and returns the right FTP reply code. Unit tests construct `ClientDriver`/`FileTransfer` directly and call their methods without spinning up `ftpserverlib` at all, since that logic lives entirely in our package; `ftpserverlib` is just the state machine that invokes it.

For the integration test we looked at `ftpserverlib`'s own test suite rather than guessing. It runs its server on `ListenAddr: "127.0.0.1:0"` and reads back the assigned port via `server.Addr()` after `Listen()`, uses the same ephemeral-port approach for PASV data connections when `PassiveTransferPortRange` is left unset, and drives itself with `github.com/drakkan/goftp` as the test client — not `github.com/jlaffaye/ftp`, despite that being this project's existing (production, soon-to-be-removed) FTP client. We follow the same pattern: ephemeral ports for both control and data channels, and `goftp` as a new test-only dependency, rather than repurposing `jlaffaye/ftp` into unfamiliar territory. `Settings.TLSRequired` defaults to `ClearOrEncrypted`, so the integration test runs plain FTP with no TLS configured at all — it doesn't need to wait on the still-open TLS-provisioning decision. Paperless-ngx is faked with `httptest.Server`, matching how the production code already talks to it over plain HTTP via resty.

This also resolves the `ct`/chart-testing question the ticket raised. The existing `ct install` step is commented out in `test-helm.yaml`, flagged in `todo.md` as flaky/restarting; the cause was the old `readinessProbe` dialing an external FTP host during startup, unreachable in CI. Once the container is the FTP endpoint, there's no outbound FTP dependency left to mock — `ct install` needs no FTP mock at all. Re-enabling it instead depends on whatever the health/readiness ticket decides about paperless-ngx reachability, not on FTP.

## Consequences

`jlaffaye/ftp` is dropped entirely (it's already being removed from production per the map's "full replacement" decision, and gains no second life as a test dependency); `goftp` is added as a new test-only dependency. The integration test needs no containers, external services, or CI changes — it's a normal in-process `go test` inside the existing `test-go.yaml` workflow.
