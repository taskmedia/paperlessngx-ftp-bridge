# Helm chart Service topology for the embedded FTP server

The control connection and every PASV data connection must reach the same pod and must be reachable at the one address the app advertises as `ftp.pasv.publicHost`, so the chart exposes both from a single `LoadBalancer` Service rather than two — splitting them would need a second external IP kept in sync via a shared-IP annotation (e.g. MetalLB's `allow-shared-ip`) for no benefit. Since Kubernetes Services can't express a port *range*, the control port and every PASV port are rendered as individual `spec.ports` entries via a Helm `range`/`untilStep` loop over `ftp.pasv.portMin`/`portMax`, mirrored onto the Deployment's `containerPorts` for `kubectl describe`/`NetworkPolicy` visibility (no functional effect on routing). `service.type` is hard-coded to `LoadBalancer` (not a value) since `NodePort` can't sanely carry ~21 ports and every target platform (k3s) already ships klipper-lb; `service.loadBalancerIP` and `service.annotations` are exposed as optional passthrough values, both empty by default, so an operator can pin a stable external IP to match `publicHost`.

The chart pins `replicas: 1`, not a `.Values` knob: there's no shared state to gain from scaling (ADR-0001's per-session `MemMapFs` is already pod-local and ephemeral), and an L4 passthrough `LoadBalancer` can't guarantee a client's PASV data connections land on the same pod as its control connection across multiple replicas — client-IP affinity doesn't survive NAT, and support varies across klipper-lb/MetalLB/cloud LBs anyway. Multi-replica would silently corrupt sessions under load rather than failing loudly, so it's locked out at the template level with an inline comment rather than left as a footgun.

The container runs fully locked down (`runAsNonRoot`, fixed non-root UID/GID, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `readOnlyRootFilesystem: true`, `seccompProfile: RuntimeDefault`) since nothing in the request path touches a real filesystem (ADR-0001: in-memory `ClientDriver`; ADR-0003: self-signed certs generated in memory, or read-only from a mounted Secret). That mounted TLS Secret, when `ftp.tls.existingSecret.name` is set, lands at a hardcoded `/etc/ftp/tls` — no volume at all in self-signed mode.

The default PASV range shipped by the chart is 20 ports (`50000`–`50019`), not the 101-port range (`50000`–`50100`) picked in ADR-0002. That default was a round conventional number, not sized to this app's actual load: a single pinned replica serving a small number of document scanners has realistic concurrent-transfer counts in the low single digits, and a large default port list is actively worse on LB implementations that cap ports-per-rule (several cloud LBs stop well short of 101 without an "all ports" flag). The `portMin`/`portMax` knob itself (ADR-0002) is unchanged — operators needing more headroom raise it themselves — only the shipped default shrank.

## Consequences

Changing `replicas` away from `1` is only possible by editing the chart template, not `values.yaml` — intentional friction against a change that looks harmless but breaks FTP sessions under concurrent clients. Operators behind a cloud LB with strict port-per-rule limits still need to check their provider's limits before raising `portMax` far beyond the default.
